# MongoDB Infrastructure — Reference Guide

How MongoDB is configured in this project, explained for future reference.

---

## Overview

MongoDB is the **read store**. Every time a Kafka event is consumed, the full employee event payload is written as a document to MongoDB. All GET endpoints read from MongoDB, not PostgreSQL.

```
Kafka Consumer (EmployeeEventConsumer)
        ↓
   employee_events  (MongoDB collection)
        ↓
GET /employees  (reads latest snapshot per employee)
```

The write path (create/update/delete) goes to PostgreSQL → Kafka → MongoDB. GET endpoints always read from MongoDB.

## Docker Compose Service

```yaml
mongodb:
  image: mongo:7
  container_name: training-mongodb
  restart: unless-stopped
  ports:
    - "27017:27017"
  volumes:
    - mongo_data:/data/db
  healthcheck:
    test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
    interval: 10s
    timeout: 5s
    retries: 5
```

| Config | Value | What it means |
|---|---|---|
| `image` | `mongo:7` | Official MongoDB 7 image |
| `ports` | `27017:27017` | Default MongoDB port — exposed so local tools (Compass, mongosh) can connect |
| `volumes` | `mongo_data:/data/db` | Named volume — data persists across container restarts |
| `healthcheck` | `db.adminCommand('ping')` | Spring Boot app won't start until MongoDB responds to ping |

**No authentication configured** — fine for local dev. In production, always set `MONGO_INITDB_ROOT_USERNAME` / `MONGO_INITDB_ROOT_PASSWORD`.

---

## Startup Order

MongoDB must be healthy before the Spring Boot app starts:

```yaml
app:
  depends_on:
    mongodb:
      condition: service_healthy
```

This prevents the app from booting before MongoDB is ready to accept connections.

## application.yml — MongoDB Config

```yaml
spring:
  data:
    mongodb:
      uri: mongodb://localhost:27017/kafka_training_events
```

| Config | Value | What it means |
|---|---|---|
| `uri` | `mongodb://localhost:27017/kafka_training_events` | Connection string — host, port, and database name in one |
| database | `kafka_training_events` | Created automatically by MongoDB on first write — no setup needed |

When running inside Docker, the app uses the environment variable override:

```yaml
SPRING_DATA_MONGODB_URI: mongodb://mongodb:27017/kafka_training_events
```

`mongodb` here is the Docker service name — containers resolve each other by service name, not `localhost`.

## Collection: `employee_events`

Every consumed Kafka event is saved as a document in this collection. There is no fixed schema — MongoDB is schemaless — but in practice every document has this shape:

| Field | Type | Source |
|---|---|---|
| `_id` | ObjectId | Auto-generated by MongoDB |
| `employeeId` | Long | From Avro event |
| `firstName` | String | From Avro event |
| `lastName` | String | From Avro event |
| `email` | String | From Avro event |
| `salary` | BigDecimal | From Avro event (logical type: decimal) |
| `hireDate` | LocalDate | From Avro event (logical type: date) |
| `department` | Object | Nested — name + location from Avro event |
| `eventType` | String | CREATED / UPDATED / DELETED |
| `eventTimestamp` | Instant | When the event was originally fired |
| `receivedAt` | Instant | When the consumer wrote it to MongoDB |

## Java Integration

### Entity

`EmployeeEventDocument` is annotated with `@Document` to map to the `employee_events` collection:

```java
@Document(collection = "employee_events")
public class EmployeeEventDocument {
    @Id
    private String id;
    private Long employeeId;
    // ... all event fields
    private Instant receivedAt;
}
```

### Repository

`EmployeeEventDocumentRepository` extends `MongoRepository` for standard CRUD, plus custom queries:

```java
public interface EmployeeEventDocumentRepository extends MongoRepository<EmployeeEventDocument, String> {
    // fetch latest event per employee for GET /employees
    // filter by department for GET /employees/department/{id}
}
```

### Consumer → MongoDB write

In `EmployeeEventConsumer`, after deserialising the Avro message, the consumer maps it to `EmployeeEventDocument`, sets `receivedAt`, and saves:

```java
document.setReceivedAt(Instant.now());
employeeEventDocumentRepository.save(document);
```

## Read Path Logic

Because every mutation fires a Kafka event, MongoDB may hold multiple documents per employee (e.g. one CREATED + two UPDATED + one DELETED). The GET endpoints resolve this by:

- **Fetching the latest event** per `employeeId` (by `eventTimestamp` descending)
- **Filtering out** employees whose latest event is `DELETED`

This means MongoDB acts as an **event log**, and the current state is derived at query time.

## Data Persistence

```yaml
volumes:
  mongo_data:
```

The named volume `mongo_data` keeps data alive when the container is stopped and restarted. To wipe all MongoDB data (e.g. for a clean test run):

```bash
docker compose down -v
docker compose up -d
```

The `-v` flag removes named volumes.
